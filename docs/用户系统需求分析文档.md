# 《LuxUmbra AI 闯关学习小程序》用户系统需求分析文档

## 1. 需求背景

当前 MVP 已跑通"输入 → 出题 → 答题 → 报告"的核心闭环，但存在以下问题：

1. **无用户身份**：每次使用都是匿名状态，无法识别用户。
2. **无数据持久化**：闯关记录和报告在页面关闭后丢失，无法回看。
3. **个人中心是空壳**："我的"页面只有占位 UI，统计数据全部写死为 0。
4. **首页信息是假数据**：工具栏的用户名"小皮"、金币"602"、已完成关卡等均为硬编码。

本次迭代目标：**引入用户系统和数据持久化，让每个用户的闯关数据可追踪、可回看、可统计。**

---

## 2. 需求批次与优先级

将全部需求拆分为 **4 个批次**，按依赖关系排列，每个批次内部可并行开发。

### 批次一：用户登录与鉴权（基础设施，所有后续功能的前置依赖）

| 编号 | 功能 | 前后端 | 说明 |
|------|------|--------|------|
| 1.1 | MySQL 数据库初始化 | 后端 | 创建 users、quiz_sessions、answer_records、reports 四张表 |
| 1.2 | 微信登录接口 | 后端 | `POST /api/v1/user/login`，接收 wx.login() 的 code，调微信 jscode2session 获取 openid，首次登录自动注册，返回 JWT token |
| 1.3 | JWT 鉴权中间件 | 后端 | 解析 Authorization header 中的 Bearer token，提取 user_id 注入请求上下文；**采用可选鉴权模式**，无 token 时不报错但不关联用户 |
| 1.4 | 前端自动登录 | 前端 | App 启动时调用 `wx.login()` 获取 code → 调后端登录接口 → 将 token 存入本地缓存 |
| 1.5 | API 请求层加 token | 前端 | 统一在 `request()` 中读取本地 token，自动附加到请求 header |

**批次一完成标志**：用户打开小程序后自动完成静默登录，后续所有接口请求自动携带 token。

---

### 批次二：数据持久化（让闯关数据落库）

| 编号 | 功能 | 前后端 | 说明 |
|------|------|--------|------|
| 2.1 | 改造出题接口 | 后端 | `POST /api/v1/quiz/generate` 生成题目后，如果请求携带 token，则将 quiz_session 存入数据库 |
| 2.2 | 改造报告接口 | 后端 | `POST /api/v1/report/generate` 生成报告后，同时将答题记录和报告存入数据库；更新用户累计经验值 |
| 2.3 | 前端答题数据提交 | 前端 | 答题完成跳转报告页时，确保答题记录完整传递给报告接口（现有逻辑已实现，仅需确认数据完整性） |

**批次二完成标志**：用户完成一次闯关后，题库、答题记录、报告都已持久化到数据库中。

---

### 批次三：用户档案与个人中心（展示真实用户数据）

| 编号 | 功能 | 前后端 | 说明 |
|------|------|--------|------|
| 3.1 | 用户档案接口 | 后端 | `GET /api/v1/user/profile`，返回：昵称、头像 URL、累计闯关次数、累计答对题数、平均正确率、总经验值 |
| 3.2 | 更新用户信息接口 | 后端 | `PUT /api/v1/user/profile`，允许用户更新昵称和头像 URL |
| 3.3 | 个人中心页改造 | 前端 | 调用档案接口，展示真实头像、昵称、统计数据；移除占位提示；支持修改昵称 |
| 3.4 | 首页用户信息展示 | 前端 | 工具栏显示真实昵称和经验值（替换硬编码的"小皮"和"602"） |

**批次三完成标志**：个人中心和首页展示的用户数据全部来自后端接口，数值随闯关变化而更新。

---

### 批次四：闯关历史与记录回看（数据利用）

| 编号 | 功能 | 前后端 | 说明 |
|------|------|--------|------|
| 4.1 | 闯关历史列表接口 | 后端 | `GET /api/v1/user/quizzes`，分页返回用户所有闯关记录（quiz_id、标题、题数、正确率、创建时间） |
| 4.2 | 闯关详情接口 | 后端 | `GET /api/v1/user/quizzes/{quiz_id}`，返回该次闯关的完整题目、答题记录和报告 |
| 4.3 | 个人中心历史列表 | 前端 | 在个人中心页面底部展示闯关历史列表，显示标题、正确率、时间 |
| 4.4 | 首页已完成关卡展示 | 前端 | 首页"已完成关卡"区域改为从接口拉取真实数据，替换当前硬编码的 RAG / 提示词工程卡片 |
| 4.5 | 历史记录点击回看 | 前端 | 点击历史记录项可跳转到报告页查看详情 |

**批次四完成标志**：用户可以在个人中心和首页看到所有历史闯关记录，并可点击查看报告详情。

## 3. 数据库选型约束

本次用户系统迭代明确使用 **MySQL**，不使用 SQLite。

原因如下：

1. 用户系统会逐步沉淀较多关系型数据，包括用户、闯关记录、答题记录、报告等，MySQL 更适合长期演进。
2. 后续还会扩展错题本、复习计划、排行榜、社交关系等能力，表关系会继续增加。
3. MySQL 在并发访问、索引设计、分页查询、统计查询、数据迁移方面更适合正式业务系统。
4. 当前阶段虽然功能量不算大，但用户系统属于基础设施，应该优先采用后续可持续扩展的数据库方案。

因此，本文档中涉及的“数据持久化”“表结构设计”“历史记录查询”等能力，默认都基于 MySQL 方案展开。

## 4. 明确不做的功能（留后续迭代）

以下功能不在本次用户系统迭代范围内：

| 功能 | 原因 |
|------|------|
| 社交 PK / 排行榜 | P2 优先级，需独立设计对战机制 |
| 错题本 + 艾宾浩斯复习 | P1 但逻辑复杂，需独立迭代 |
| 分享海报生成 | 需 Canvas 绘制，独立迭代 |
| VIP 付费 / 商业化 | P3 优先级 |
| 多源输入（PDF / URL / 视频） | P1 但属于输入扩展，与用户系统无关 |
| 首页"未完成关卡"功能 | 当前硬编码的"数学闯关""科学闯关"仅为原型占位，本次不改造为真实功能，保持原样即可 |

## 5. 经验值规则（MVP 简化版）

| 场景 | 经验值 |
|------|--------|
| 完成一次闯关（不论对错） | +10 XP |
| 每答对一题额外奖励 | +2 XP |

示例：5 题闯关，答对 4 题 → 10 + 4×2 = 18 XP

---

## 6. 验收标准

### 批次一验收
- [ ] 小程序启动后自动完成静默登录，本地缓存中有有效 token
- [ ] 后端 users 表中可查到新注册用户
- [ ] 所有后续接口请求中 header 携带正确的 Authorization

### 批次二验收
- [ ] 完成一次完整闯关后，quiz_sessions、answer_records、reports 表中均有对应记录
- [ ] 无 token 时接口仍正常工作（匿名模式），但不写入数据库

### 批次三验收
- [ ] 个人中心页显示真实的闯关次数、答对题数、平均正确率
- [ ] 首页工具栏显示真实昵称和经验值
- [ ] 做完一次新闯关后，统计数据自动更新

### 批次四验收
- [ ] 个人中心展示闯关历史列表，最近闯关排在最前
- [ ] 首页"已完成关卡"显示真实历史记录
- [ ] 点击历史记录能跳转查看报告详情
